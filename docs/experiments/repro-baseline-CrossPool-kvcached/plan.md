# CrossPool 论文 kvcached 对比基线复跑计划

> 最后编辑时间： 2026-11-20 02:00:00

## 1. 实验目标与总体设计

### 1.1 目标与前置状态

本计划用于复跑 CrossPool 论文图 7 中的 `kvcached`（Chimera）对比基线，测量三种 MoE 模型在五卡混部场景下的尾部生成延迟、吞吐量及 KV 空间占用。论文原始实验数据仅作参考，本次实验与论文条件不同，**正式基线数据全部以本轮重跑结果为准**。

### 1.2 实验矩阵（4 × 2 × 3）

论文图 7 对比了 Static Partition、kvcached 与 CrossPool。本轮针对 `kvcached` 设置 **8 个实验条件**，每个条件重复 **3 个独立负载 seed**，共 **24 次**测量：

* **到达率（4 档）**：单模型 0.2、0.5、0.8、1.0 请求/秒（合计 0.6、1.5、2.4、3.0 请求/秒）。
* **MPS 状态（2 态）**：开启 vs 关闭（论文未明确 MPS 状态，两态均测并作配对对照）。
* **配对原则**：同一到达率与 seed 下的 MPS 开/关两组，使用完全相同的请求内容、计划到达时刻和预热请求，且在时间上相邻运行、交替先后顺序，以削弱环境漂移的影响。

### 1.3 与原论文的已知条件差异

与 CrossPool 论文相比，本轮存在以下明确差异，后续对比分析时须如实说明：

1. **Prefill/Decode 策略**：论文采用 P/D 分离并重点比较 decode；本轮沿用 P/D 不分离（混部）策略。
2. **模型版本**：论文写作 `DeepSeek-V2-Lite`；本轮按约定使用远端现有的 `DeepSeek-V2-Lite-Chat`（需随结果记录具体权重与 tokenizer 版本，论文是否同为 Chat 版尚未确认）。
3. **数据集子集与预处理**：论文仅引用了同一个 HuggingFace 仓库，未公布具体文件版本与清洗规则；本轮采用普通 V3 分割文件及本地固定的预处理规则。

## 2. 硬件拓扑与服务部署规范

### 2.1 硬件资源与模型放置

底层采用 **5 张 A100 GPU**（每卡 40GB HBM，合计 200GB），卡间通过 NVLink 互联。文档中的 `GPU0`–`GPU4` 为逻辑编号，实际执行时需映射到具体物理设备并记录映射关系。

三模型共占用 **10 个 GPU rank**（每卡 2 个 rank），模型权重与对应请求的 KV cache 同卡存放。具体配置依据论文 §5.1、Table 2 及既定并行方案固定如下：

| 模型精确名称 | 逻辑 GPU 集合 | TP / DP | DP attention | GPU rank 数 |
| :--- | :--- | :---: | :---: | :---: |
| `Qwen3-30B-A3B` | GPU0、GPU1、GPU2、GPU3 | 4 / 1 | 关闭 | 4 |
| `GLM-4.7-Flash` | GPU1、GPU2、GPU3、GPU4 | 4 / 4 | 开启 | 4 |
| `DeepSeek-V2-Lite-Chat` | GPU0、GPU4 | 2 / 2 | 开启 | 2 |

共置关系：`GPU0` 共置 Qwen 与 DeepSeek；`GPU1`–`GPU3` 共置 Qwen 与 GLM；`GPU4` 共置 GLM 与 DeepSeek。

### 2.2 控制变量与 MPS 校验

MPS 开/关两组必须保持以下条件完全一致：模型权重与 tokenizer、总硬件资源、放置与并行配置、服务启动参数及观测方式。

* **MPS 启动校验**：MPS 开启组必须确认 **GPU MPS server 先于模型服务启动**（仅 control daemon 就绪不足以证明生效），并记录实际接入状态。
* **作用范围**：开/关两组均覆盖相同的 5 张卡和全部 10 个 rank；只管理本次实验自有的 MPS 实例，不干扰同机其他作业。

### 2.3 显存与缓存策略

* **KV 动态分配**：不设人为固定的全局 KV 预算或单模型配额。KV 空间动态使用扣除模型权重、工作区（workspace）及安全余量后的剩余可用显存。各实验组保持相同的余量策略和模型加载顺序。
* **前缀缓存**：关闭跨请求前缀缓存（cross-request prefix caching），仅保留单次请求内的 KV 使用。

### 3.2 清洗、拼接与过滤规则

按以下顺序构建所有实验共用的冻结输入池：

1. **会话还原**：以原始会话为单位恢复消息顺序，对重复片段去重。仅当重叠消息的角色和正文完全一致时才接续；缺少起点、存在消息缺口或内容冲突的会话直接剔除。
2. **有效前缀提取**：从会话首条消息起提取连续的“提问—回答”对。遇到非法角色或空白提问/回答时立即截断，仅保留此前完整的轮次；无完整轮次的会话剔除。空白判定与正文保留分离：非空正文逐字符原样保留（含原空格、换行与 Unicode 字符）。
3. **文本格式模板**：每条候选输入包含“此前最近两轮完整问答（不足两轮则全部保留）+ 当前问题”。参考回答仅作来源追溯，不参与测试。格式如下（各标签间使用实际换行，冒号后保留一个空格，末尾 `Assistant:` 后无空格和换行）：

   ```text
   Human: <历史问题>
   Assistant: <历史回答>
   Human: <当前问题>
   Assistant:
   ```

4. **三模型长度交集过滤**：使用三个模型各自实际使用的 tokenizer（含与服务端一致的起始符及特殊 token）对完整输入编码。过滤条件为三个模型必须同时满足 `输入 token 数 + 1024 <= 8192` 且不超过模型实际可接收上下文边界，取三者合格轮次的交集。
5. **会话等权抽样与冻结**：将合格会话与轮次按稳定标识排序，使用固定数据 seed **`20261212`**，从每个有合格轮次的会话中等概率抽取 1 轮（使每个会话贡献 1 条输入）。冻结最终输入池、会话轮次映射及内容哈希。

### 3.3 数据集统计留档

需记录并报告：数据来源信息、清洗规则、抽样 seed、各阶段保留/剔除条数、冻结池总大小；三个模型输入 token 长度的 `min / P50 / P90 / P95 / P99 / max`，以及历史轮数为 `0 / 1 / 2` 的占比。后续每次压测还需单独报告实际请求的长度分布与抽样重复率。

## 4. 压测负载与执行流程

### 4.1 负载配置与生成参数

* **到达过程**：三个模型各自独立遵循泊松（Poisson）到达过程，各档位每模型到达率相同：

  | 单模型名义到达率 (req/s) | 三模型合计名义到达率 (req/s) | 配对条件 |
  | :---: | :---: | :--- |
  | 0.2 | 0.6 | MPS 开、关 |
  | 0.5 | 1.5 | MPS 开、关 |
  | 0.8 | 2.4 | MPS 开、关 |
  | 1.0 | 3.0 | MPS 开、关 |

* **请求抽样**：各模型从冻结输入池中独立、**有放回**抽样（跨模型共享总池，各模型实际抽到的序列分别记录）。使用 3 个工程固定的独立负载 seed（与数据抽样 seed 独立），保存各 seed 的请求计划并在配对两态间完全复用。
* **生成参数**：`temperature = 0`，最大输出 `1024` tokens，尊重 EOS 自然终止。按实际生成内容统计；自然结束（EOS）和达到 1024 上限均视为成功，参考回答长度不作为生成预算。

### 4.2 单次运行流程

每次运行均从一致的服务初始状态启动：

1. **预热（Warmup）**：正式发压前，每个模型串行发送 10 个预热请求。预热结果单独统计，需记录其与正式输入池的交集，以及预热前后的系统资源状态。
2. **正式发压（到达窗 $T = 600$ 秒）**：所有模型预热完毕的时刻记为测量原点 **$T_0$**。在 $[0, T)$ 内按预定到达时刻发送请求。
3. **排空（Drain）**：$T$ 时刻后停止产生新请求，继续发送 $T$ 窗内已排队的请求，直至全部请求达到终态。**不主动设置客户端 HTTP 超时或全局排空截止时间**，并如实记录 $T$ 之后的迟到发送（注：若遇服务卡死、断流或外部中断，需如实记录异常，不强求全数成功）。

### 4.3 算力预算与异常重跑规则

* **时间估算**：24 次运行 × 10 分钟 = **4 小时**正式压测（5 卡共 **20 卡时**），启动、预热、MPS 切换与排空耗时另计。
* **无效重跑**：若某次运行被判定为整组无效，重跑记录需独立保存。原尝试有效则以原尝试为准；仅当原尝试无效时采用一次有效复跑；若两次均无效，则记为缺测。

## 5. 观测采集与数据留存

### 5.1 请求级时间轴与原始 Trace

所有事件统一在同一时间轴下记录以下 5 个关键时刻：

* **$A$**：计划到达时刻
* **$E$**：实际进入客户端队列时刻
* **$H$**：客户端开始发送时刻
* **$F$**：客户端首次观测到正输出 token 的时刻
* **$D$**：请求达到终态的时刻

**原始记录留存**：逐条保存可恢复的原始输入、输入标识与计数、计划与实际请求记录、各步输出观测（沿用现有 `usage` 采集能力，不新建复杂采集系统）、`finish_reason` 与最终状态。原始记录与后续脚本重算的派生结果必须分开存放。

### 5.2 资源与 KV 时序采集

* **采样时机**：模型加载后、预热后、发压与排空期间、排空结束后。记录完整采样时刻、间隔、缺失及报错，峰值指标须明确标注为“采样峰值”。
* **采集维度**：按模型、rank、GPU 及可识别的并行分片，分别记录物理总/空闲/已用显存、KV 物理映射量、预留量、逻辑分配量、虚拟上限及逻辑 token 容量。（仅在直接可观测时才报告实际活跃 token 数，不使用已分配块数（allocated blocks）代替）
* **几何与架构元数据**：留存每套模型的架构类型（MLA 或 MHA/GQA）、KV 数据类型、层数、存储维度，以及 rank/TP/DP 分片、复制与请求路由关系。
  * 容量换算公式：`floor(有效字节数 / 对应作用域单 token KV 字节数)`，须明确页粒度、对齐及预留开销。
  * MLA 架构不适用该公式。

## 6. 指标定义与统计分析口径

### 6.1 延迟指标（主分布统计对象：成功请求）

1. **Token 加权 TBT / ITL（核心指标，报告 P95、P99）**：
   设相邻两次观测到的正输出 token 增量为 $\delta$、时间间隔为 $g$，则区间单 token 耗时为 $g/\delta$，权重为 $\delta$。需分别报告三组分布及各自覆盖率、权重总和：
   * 单 token 直接观测（$\delta = 1$）
   * 多 token 合并块估计（$\delta > 1$）
   * 二者合并分布
2. **请求等权 ITL 与 TPOT（报告 P95、P99）**：
   * **平均 ITL**：单条请求内各正 token 区间值（$g/\delta$）的算术平均。
   * **TPOT**：$(D - F) / (\text{输出 token 数} - 1)$。
   * *注：输出不足 2 个 token 的请求，上述两项记为缺失，需报告有效请求数及尾部样本稀疏情况。*
3. **首字与端到端延迟**：
   * **TTFT**：计划起算 ($F-A$)、入队起算 ($F-E$)、发送起算 ($F-H$)。
   * **端到端延迟**：计划起算 ($D-A$)、入队起算 ($D-E$)、发送起算 ($D-H$)。
   * 需同步并列实际输出长度、EOS/长度上限占比及失败比例。

### 6.2 到达质量（统计对象：全部计划测量请求）

对具备对应时间戳的请求统计 **P50 / P95 / P99**：

* 入队迟到：$E - A$
* 客户端队列等待：$H - E$
* 计划至发送延迟：$H - A$
同时必须报告：计划总数、各指标有效样本数、时间戳缺失数、明确未发送数、发送状态未知数。

### 6.3 请求终态、速率与吞吐

所有吞吐统计均排除预热请求，且分子分母严格对齐同一时间窗口。

* **终态分类**：每次物理尝试恰对应一种终态——**成功、失败**（须细分“超时”与“其他失败”，不自动重试）、**取消、未发送**。若遇外部中断，须单独标明已知终态、未发送及尚无终态的请求；缺失终态单列为“证据缺失”，不得计入成功或正常排空。
* **发压期速率（时间窗 $[0, T)$）**：分别将窗内计划到达数、实际发送数、成功完成数、已发送请求的全部终态数除以 $T$；另按固定左闭右开时间桶记录各模型及合计的计划/实际发送速率。窗内发送比例的分母为全部计划测量请求数。
* **完整窗口 $W$ 与吞吐**：
  * 正常排空时，$W = \max(T, \text{最后一条请求终态时间})$；若发生中断，$W$ 取实际封窗时间并标注“未完整排空”。需记录 $T$、$W$、排空耗时 $\max(0, W-T)$ 及 $T$ 时刻的排队/在途状态。
  * **成功请求吞吐** = 窗内成功请求数 $/ W$
  * **成功输入吞吐** = 窗内成功请求的输入 token 总数（含缓存命中部分）$/ W$
  * **成功输出吞吐** = 窗内成功请求观测到的正输出增量总数 $/ W$
  * **非成功输出单列**：失败或取消请求的已观测部分输出需单独统计（细分超时与其他失败，缺失不填零）；封窗后的终止与输出亦须单列。若额外报告“总观测输出吞吐”，其定义固定为 `（成功输出 + 非成功部分输出）/ W`，并在名称上与成功输出吞吐严格区分。
  * *时间桶呈现说明*：发压期与排空期的时间桶须分开展示；排空是停止到达后的恢复阶段，若系统在发压期过载，即使最终排空完成，也不得将全窗口视作稳态运行。

### 6.4 理想序列 KV 估算与拐点归因

* **理想 KV 估算**：令 $P$、$O$ 为服务端最终统计的输入、输出 token 数，用 `(P + O) × 对应 rank 的单 token KV 字节数` 估算完整序列的理想 KV 占用（不减 1，不用可见文本重新分词替代服务端计数；仅有部分进度的失败请求不作完整序列估算；不需要为此额外保存完整回答或 token IDs）。该值仅为理论参考，不代表某时刻实际物理驻留或预留量。
* **容量与延迟分析**：结合请求排队、重算、资源占用与失败时间序列，解释容量压力与尾延迟拐点，论述时须严格区分“直接运行观察”与“机制推断”。

### 6.5 跨 Seed 汇总、配对比较与展示规范

* **跨 Seed 统计**：每个 seed 独立计算分位数（token 加权分位数采用按权重展开等价的线性插值；请求等权指标每请求 1 样本）、吞吐、失败率及资源统计，最终报告 3 个 seed 的**中位数**与**范围（min / max）**。需在每次运行中分别汇报有效请求数、输出计数和间隔权重总和。
  * *样本稀疏提示*：在 0.2 RPS 下，600 秒每模型仅约 120 条请求，请求级 P99 尾部样本明显不足，且同请求内的 token 间隔存在相关性，报告时须如实标注（本轮 10 分钟 × 3 次是本地实验选择，不构成尾部分位数已收敛或 MLPerf 合规证明；若证据不足，后续可对配对两态追加测量）。
* **MPS 效应对比**：针对每档负载、每个 seed 和每个模型，分别计算 `MPS 开 - MPS 关`（绝对差）与 `MPS 开 / MPS 关`（比值，分母为 0 记未定义），汇总跨 seed 差值范围。
* **核心图表**：
  1. 分模型展示：`到达率 — P95/P99 延迟`、`吞吐量`、`失败率` 曲线。
  2. 共享时间轴展示：KV 占用、请求排队与延迟的联动时序图。
  3. 比较展示任何性能变化时，须同步呈现到达质量、失败率与数据缺失情况。
