# 自动实验实施计划

> 最后编辑时间： 2026-11-20 02:00:00

## 1. 目标定位与上游复用边界

本计划规定如何开发一个**轻量级顺序调度外层（薄外层）**，用于在执行机上一次性无人值守跑完 24 组对比实验。

### 1.1 核心运行目标

* **严格顺序与断 SSH 续航**：执行机启动后严格串行遍历 24 个 case，SSH 或用户本机断开后继续运行。
* **故障隔离**：单个 case 发生不可恢复故障时，安全清理该 case 的外部资源后可继续下一组；若发生影响全局的共享故障，则立即阻塞批次。
* **超时边界**：正式测量不设置主动 HTTP 超时或全局排空截止时间（deadline），也不在后台暗加 stall watchdog。若遇永久挂起，系统不会自动掐断，因此**不承诺有限的总墙钟时间**。

### 1.2 上游框架（CrossPool）复用清单

核心压测逻辑复用固定版本 CrossPool 仓库中的现有实现（核心代码位于 `src/xpool-dev/xbench/harness/serving/`，结果存储位于 `src/xpool-dev/xkit/`；以下标注源码依据源自前期核查与复审）。**若后续需核对源码，须先阅读子模块下的 `AGENTS` 说明。**

| 职责模块 | 复用上游内容及源码依据 | 明确禁止事项（开发红线） |
| :--- | :--- | :--- |
| **多模型与请求执行** | 复用 `BenchCatalog` / `ClientBenchCase` 三目标并发、原生到达调度、FIFO 队列、排空、请求失败后继续、事件及基础指标（`case.py:139—196`、`client.py:309—395`）。 | 不得重写请求失败循环或请求状态机。 |
| **输入与配对资产** | 复用原生 `prepared workload`、`prompts`/`trace`/`warmup` 文件及哈希（`runner.py:239—280`、`workload.py:92—118`、`197—214`）。 | 不得新建随机 trace 抽样引擎。 |
| **产物与断点恢复** | 复用原生 `run/repetition/attempt` 目录结构、日志、排他目录、`flock` 锁、原子 checkpoint、`continue`、成功跳过及显式 `--rerun-failure`（`runner.py:284—317`、`457—607`，`results.py:26—53`、`104—169`）。 | 不得另造一套功能重复的目录恢复或重试引擎。 |
| **本地已有脚本** | 复用现有自有 CLI、服务启动命令/环境构建器、进程组清理、预检及独立客户端副本准备机制。 | 禁止修改上游子模块或共享安装目录；确需兼容适配时，须在独立副本中验证缺口并记录补丁身份。 |

**为什么必须加一层薄外层（原生接口的局限）：**

1. 原生 `repetitions` 会复用同一份 `prepared workload`，不会切换随机 seed。
2. 原生 `--all` 或多选 case 可能触发并发执行，无法保证严格顺序和干净的独占环境。
3. 原生 client 仅连接外部 URL，不负责管理 SGLang 服务或 MPS 生命周期；且不能用原生的 CrossPool daemon、attention MPS 或 PD 分离拓扑替代 06 计划的独立服务方案。
4. 现有的 `smoke`/`validate` 仅针对单目标与有限等待，保留其原有语义不变；正式入口仅额外传入“原生无请求截止”配置并移除外层测量等待截止（注意：启动就绪保护和清理超时保护与测量截止相互独立）。

## 2. 配置规范、实验矩阵与配对身份

### 2.1 配置文件与参数解析优先级

使用标准库可读的 JSON 配置文件，禁止在执行器代码中硬编码模型名、设备、负载或规模。

配置须完整覆盖：模型/权重/tokenizer、TP/DP/attention 开关、逻辑放置、物理设备映射、端口/Python 解释器、服务启动参数、MPS 私有路径、输入资产、负载 seed、RPS、预热参数、测量窗口、生成参数及输出路径。

本轮配置严格对齐计划（三模型、五张 40GB A100 共享关系、10 个 rank、PD 不分离、关跨请求前缀缓存、动态 KV 及一致的余量/加载顺序）。

* **参数优先级**：`显式 CLI 参数 > 配置文件显式值 > 已载入的 KVREPRO_* 环境变量 > 通用默认值`。拒绝存在歧义的多服务覆盖，启动前冻结最终生效值及来源；**不自动读取 `.env` 等环境文件，不转储整个系统环境变量**。
* **GPU 设备可见性**：未显式指定 devices 时，保留 `CUDA_VISIBLE_DEVICES` 原值（区分未设置与空字符串）；若显式指定设备，**仅作用于对应的服务子进程**。TP/DP 配置相互独立，绝不根据可见卡数反向猜测并行度。预检阶段使用的隔离禁用环境仅限预检使用。

### 2.2 实验矩阵展开与顺序策略

* **矩阵规模**：离线展开 `4 档 RPS (0.2 / 0.5 / 0.8 / 1.0) × 3 个独立负载 seed × MPS 两态 (开/关) = 24 个 case`。
* **负载 Seed 建议**：固定为 **`20261213`、`20261214`、`20261215`**（与数据抽样 seed `20261212` 严格区分）。
* **执行顺序**：同一个 `(RPS, 负载 seed)` 下的 MPS 开/关两个 case 相邻排布，并按重复序号交替“先开后关 / 先关后开”。每次只调用一个原生 client case（设 `repetitions=1`），完全清理外部服务并验证后，才进入下一个 case。

### 2.3 稳定身份标识（`pair_id` 与 `case_id`）

* **`pair_id`**：由冻结输入、三模型稳定身份、负载 seed/RPS、原生工作负载规则、预热数、生成参数、窗口时长等规范化内容的哈希摘要生成，**不含 MPS 状态**。
* **`case_id`**：在 `pair_id` 基础上加入 MPS 状态及执行条件指纹。
* **计算约束**：ID 不得依赖矩阵序号、时间戳、临时端口号或 Python 内置 `hash()`。配置文件中的相对路径在启动时基于配置文件目录解析为绝对路径并冻结。启动前须校验引用完整性、ID 重复性、参数合法性、拓扑一致性及资产可读性；若实验条件变更，必须新建批次身份，不得混用旧批次目录。同时记录代码版本、独立客户端补丁身份、资产哈希及实际设备映射。

## 3. 跨 Run 资产冻结与输入适配方案

由于原生框架的 `prepare_case` 在新建 run 时会无条件重新调用 `prepare_workload`，且 CLI 不支持导入外部 prepared 数据，而 `continue` 又只能恢复原 run 配置、无法用来创建“MPS 另一态”的新 run（见 `runner.py:239—254, 465—512, 587—590`，`run.py:21—49`），因此需要为配对设计做一处**最小适配**：

### 3.1 独立客户端副本的最小补丁

仅在**独立客户端副本**的 `prepare_case` 获取 workload 处，增加一个可选的“冻结 prepared 来源”参数及对应传入入口（记录该副本的补丁身份；不改上游子模块/共享安装，不扩展调度或恢复引擎）：

1. **每对的首态**：正常调用原生 `prepare_workload` 生成一次资产并冻结保存。
2. **每对的另一态（及获准的新 run 复跑）**：通过上述适配入口传入首态的冻结目录，调用 `PreparedWorkload.load(source, case=current_case)` 绑定当前 case，**不重新抽样**。

### 3.2 严格校验与物化规则

加载器本身只负责读文件，**不能仅凭“seed 相同”或“加载成功”就认定配对成立**。适配边界和物化流程须执行以下检查：

1. **适配前校验**：核对冻结来源合法性、配对条件一致、三模型稳定 ID 及顺序、seed/RPS、输入及生成参数、预热数、到达窗/时间桶宽度，以及四类核心文件的 SHA256 与原生内容哈希。
2. **资产物化**：将冻结的四类资产——`workload.json`、`prompts.jsonl`、`trace.jsonl`、`warmup.jsonl`（`runner.py:245—254`）——按原生目录布局物化（拷贝）到当前 run 的 `cases/<当前case_id>/` 目录内，保持原 schema、相对输入引用及 JSONL 字节一致性，并在本 run 目录内复核加载与哈希。**严禁使用跨目录 symlink 或外部路径引用**（`PreparedWorkload.load` 解析后的路径必须位于本 case 目录内，`workload.py:92—118`）。
3. **Manifest 构建**：`case.json` 由当前 case 独立构建，记录本态身份、实际外部服务 metadata 及原始内容哈希，**不得整份复制配对另一态的 manifest**；原生 manifest 机制仍将继续校验哈希、桶宽与窗口（`measure.py:82—95`）。其余 run/repetition/attempt、锁、checkpoint 和 `continue` 流程保持原生，恢复时只消费各自 run 目录下的物化资产。
4. **数据集边界**：计划中的数据版本、普通 V3 文件、本地校验 hash、两轮模板、三 tokenizer 交集及 8192/1024 限制全部保留；仅补充本地预处理结果到原生 `prompts` 的映射，不扩采完整回答、token IDs 或逐请求物理页证据。

## 4. 薄外层架构、目录组织与离线派生

### 4.1 代码结构与开发约束

* 自有代码置于 `src/`，测试置于 `tests/`，不引入插件体系、数据库、远端管理平台或重型框架。
* **建议划分为三个核心模块**：
  1. **配置与矩阵适配模块**（参数解析、展开与身份校验）
  2. **顺序驱动与原生调用适配模块**（批次控制、调起单个原生 client、状态审计）
  3. **独立服务与 MPS 资源管理模块**（SGLang+kvcached/MPS 启停、监控与清理）
* **编码规范**：单个函数尽量不超过 20 物理行，以新人易读为优先（但不要机械碎片化），复杂归属校验与统计公式须配清晰注释。KV 证据收集与研究汇总沿现有证据路径扩展；须先逐项完成指标与原生字段的映射，再只补确实缺失的 KV 序列、研究窗口或统计口径，不默认另写一套测量模块。

### 4.2 目录、索引与锁机制

* **产物分离**：批次目录仅存放**冻结配置、顺序 manifest、外层 runner 日志、最小批次索引、外部资源/KV 证据**；核心压测数据保留在各自的**原生 `run/repetition/attempt` 目录**内，不整套复制或维护平行的 attempt 编号。stdout/stderr 持续流式写入文件，服务/MPS 与 KV 证据通过原生 attempt 引用进行关联。创建或恢复均不得覆盖原始证据。
* **最小批次索引**：复用既有文件锁与原子写工具维护，记录 `pair/case -> 原生 run 及 attempt 引用`、`prepared 资产引用`、`研究采用理由` 及 `外部资源归属与清理结论`。该索引只用于弥补原生框架“不知道 24 项顺序、跨 run 配对和外部服务所有权”的空白，**不是第二份请求状态或原生 checkpoint，不能仅凭索引自行宣布测量成功**（进度须对照原生产物与清理证据核对）。
* **双层锁职责**：原生 `RunStore` 锁保护单个 run 目录；外层仅需一个**批次级单执行器锁**，防止同时启动两个驱动进程并发跑不同 case。（注：文件锁不代表 GPU 使用授权）。

### 4.3 离线指标派生规范

原始事件、usage/finish/outcome 及基础指标优先复用原生输出。06 计划要求的 `A/E/H/F/D` 时间戳、正输出增量、同窗吞吐、token 加权分位数与覆盖率等，通过字段映射和**离线派生脚本**计算，缺失项明确标记，**绝不修改原始日志去迎合统计**。
KV 附加采样须保留模型/rank/GPU、采样时刻、间隙及 MLA/MHA 几何信息；逻辑理想 KV 与物理占用分列，不得用块数冒充活跃 token，不得对 MLA 或跨卡情况机械除 TP 或乘 DP；严格区分“直接观测事实”与“结合源码的机制推断”。

## 5. 单 Case 执行流水线与运行域管理

### 5.1 单 Case 标准执行流程

外层严格按以下 9 步串行执行每个 case：

1. **预检**：核验共享环境前提与自有资源可用性。
2. **登记意图**：在运行域中登记本次启动意图与进程归属信息。
3. **启动 MPS（仅开态）**：先启动本组私有的 GPU MPS server。
4. **启动模型服务**：按冻结顺序启动三个 SGLang+kvcached 服务，校验所有 rank 实际接入状态、路由与前缀缓存关闭状态。
5. **执行原生压测**：调用单 case 原生客户端（`repetitions=1`）。由原生内部完成每模型串行 10 次预热 $\rightarrow$ 全部预热后确立 $T_0$ $\rightarrow$ 600 秒到达窗 $\rightarrow$ 无截止排空（$T$ 后继续发送积压请求，外层绝不截断）。
6. **保存证据**：归档原生测量产物与外部 KV/资源采集证据。
7. **逆序清理与校验**：按与启动相反的顺序停止模型服务及私有 MPS server，核验进程退出与显存释放。
8. **审计有效性**：根据计划口径审计本 case 研究有效性并更新采用关系。
9. **推进**：清理确认无误后，进入下一个 case。

### 5.2 自有运行域与隔离边界

外层在启动服务前必须登记：**主机名/boot ID、PID/PGID、启动时间、命令指纹、端口、以及私有 MPS pipe/log 与 IPC 身份**。

* **精准管控**：外层只管理“可证明归属于自己”的服务、controller 和 MPS server。
  * **MPS 开态**：必须证明 MPS server 先于所有模型服务启动，且 10 个 rank 全部实际接入。
  * **MPS 关态**：必须核验所有模型服务均未接入任何 MPS。
* **共享机器边界**：严禁关闭他人的 MPS daemon、执行全局 quit 或重置 GPU。注意：私有路径隔离并不代表在共享机器上绝对无冲突，若无法保证环境独占或安全隔离，应主动阻塞并协调。

## 6. 故障处理、断点恢复与复跑规则

### 6.1 四维独立状态体系

系统分别记录以下四项状态，不维护第二套请求失败重试逻辑：

1. 原生进程退出码与 attempt 结果
2. 请求终态及证据完整性
3. 外部基础设施及清理结论
4. 计划下的研究有效性

**特别口径**：原生客户端只要有任意一条请求未成功，就可能返回非零退出码（`code 1`），但这**不代表实验失败**——只要证据充分，该次运行在研究上仍有效，需保留失败比例并采用该尝试（禁止因此直接触发 `--rerun-failure` 或删除原尝试）。此外，原生的 `evidence_missing` 即使在原生层面归为 `failed`，在研究派生层也必须单列为“未知/证据缺失”，不得伪造失败时间、成功或正常排空。

### 6.2 异常情况处理矩阵

| 异常场景 | 外层执行动作 |
| :--- | :--- |
| **单条请求 HTTP/SSE/协议失败** | 交由原生客户端记录，继续执行既定请求计划与排空；**严禁**触发整 case 中止或重发请求。 |
| **原生正常结束，含部分请求失败但证据足够** | 按 06 规则判定研究有效性，记录原生非零退出码与采用理由，清理并核验外部资源后**继续下一 case**。 |
| **自有服务确定死亡、客户端整体崩溃、执行链路不可继续** | 记录实际中断/封窗时刻与部分证据，中止本 case 并清理；未终态请求保留“未知”。**仅当清理干净且共享前提正常时才允许继续下一 case**（严禁把单请求异常升级为 case 故障）。 |
| **配置/资产错误或共享域故障** | 尽量在启动前拦截；若出现共享解释器/模型资产损坏、GPU 不可用、磁盘不可写、MPS 域异常或清理结果不明，**立即阻塞整批运行**，未运行项不再启动。 |
| **进程仍存活但 HTTP/排空长时间无新进展** | **保持等待**，可在日志中提示停滞状态，但绝不自动判失败、不跳过、不增加 stall watchdog。 |
| **收到 `SIGINT`/`SIGTERM` 或执行器自身崩溃** | 若信号可捕获：停止推进后续 case，通过原生取消/封存机制收尾，清理自有外部资源后停止批次；若遇 `SIGKILL`/掉电：交由后续显式 `resume` 审计恢复。 |

**死亡监控与超时保护区分**：由于原生 `check_alive` 不监测外部服务进程，外层必须补充**“进程确定死亡”监控**（注意：是基于 PID/存活状态确认死亡，绝非基于无进度去猜测死亡）。服务启动就绪等待及收尾阶段的 `SIGTERM -> SIGKILL` 强制清理可以设置独立的、有记录的有限保护超时，但**绝不应用于 HTTP 请求或排空阶段**。若底层或外部环境实际触发了超时/服务限制，按 06 规范如实记录。批次汇总报告须拆分展示“已完成、无效/缺测、等待中、阻塞、信号中断”各类数量并保留底层退出码，不得用单一总码掩盖故障原因。

### 6.3 断点恢复（`resume`）审计规则

执行机重启或异常中断后，通过人工显式触发 `resume` 恢复批次（**不允许未处理完待恢复状态或共享故障前直接发新压**）：

1. **获取批次锁并审计运行域**：
   * 若检测到原驱动进程仍存活，直接拒绝第二个执行器启动。
   * 发现可证明归属于本批次的孤儿进程，须先显式清理并确认完成；若发现归属未知的残留进程，直接阻塞，**绝不盲目重启活进程或仅凭旧 PID 直接 `kill`**。
   * 主机 `boot ID` 变化只能证明旧进程已消失，不能证明之前的测量已完成。外部资源审计无法由原生的 `continue` 替代。
2. **调用原生 `continue`**：
   * 原生 `continue` 会复用原配置与物化资产，验证并跳过已成功的 attempt，且**默认也跳过已尝试但失败的 run**（保留非零码），不会从单条请求偏移处续跑。
   * 外层负责核对身份、研究有效性及外部清理结论，不重新实现目录扫描恢复逻辑。若原生因缺失 prepared/case 资产而拒绝恢复，如实保留拒绝和证据缺口，不得伪造完整结果或承诺任意崩溃点都能无损续跑。
3. **非原子崩溃窗口**：进程启动与意图登记之间、产物写完与批次索引更新之间均可能发生崩溃（checkpoint 不保证恰好一次）。遇记录缺失或截断时须原样保留并审计，绝不能仅凭目录存在与否来判定“已成功”或“未运行”。

### 6.4 无效 Case 的复跑与结果采用规则

* **复跑触发条件**：**仅当原尝试被判定为“研究无效”时**，才在明确选中该 case 并记录理由后执行一次复跑（不默认自动重试，不批量重跑所有非零退出码 run；若配置发生修改，必须新建批次）。
* **复跑操作路径**：
  * 若原生接口允许，对该 case 对应的 run 显式执行 `continue --rerun-failure` 生成新 attempt。
  * 若原尝试原生成功（返回 0）但研究无效（此时原生接口禁止在原 run 上重跑），则显式新建一个原生 run 并映射到同一 case 的复跑角色，通过第 3 节适配入口物化原 prepared 资产，**保留旧 run 不删除**。
* **最终采用规则**：按 06 规定，原尝试研究有效就采用原尝试；仅原尝试无效时，采用一次有效的复跑结果；若两次均无效，则记为缺测。**批次索引中的采用关系必须精确指向具体的 `attempt` 引用，禁止默认把原生 `latest` 当作研究采用结果。**

## 7. 无人值守执行方案（断 SSH 保障）

推荐在执行机上利用现有的 **`tmux`** 会话托管单个前台顺序驱动进程，作为保障 SSH 或本地终端断开后持续运行的标准方案：

* **启动准备**：启动记录须写明配置文件绝对路径、已协调的物理设备映射、输出根目录、文件日志重定向路径及原生 run 引用；运行日志必须开启**无缓冲输出**（unbuffered），后续重连只通过查看日志文件跟踪进度。
* **生效前提与预验**：需确认目标机 `tmux` 可用、用户注销策略不会自动回收后台进程、且存储/资产路径持续可访问。正式上 GPU 前，**必须先用 CPU 替身（stub）跑通完整流程验证**。
* **边界说明**：`tmux` 仅保障用户断开 SSH 后任务不中断，**不保障执行机物理重启**。不配置开机自启（Auto-Restart），若执行机重启，须由人工显式执行 `resume` 审计恢复。仅当现有环境确实会强制回收用户 `tmux` 会话时，才去评估系统已有的 `systemd` 用户级服务及权限，不为此引入新运维平台。
